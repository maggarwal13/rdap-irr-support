Abstract

   The Registration Data Access Protocol (RDAP) is used by Regional
   Internet Registries (RIRs) and Domain Name Registries (DNRs) to
   provide access to their resource registration information.  The core
   specifications for RDAP define core object types, but they do not
   contain objects for the Internet Routing Registry (IRR).  This
   document is intended to address this gap.

1.  Introduction

   The Registration Data Access Protocol (RDAP) [RFC7480] is used by
   Regional Internet Registries (RIRs) and Domain Name Registries (DNRs)
   to provide access to their resource registration information.  The
   core specifications for RDAP define core object types, but they do
   not contain objects for the Internet Routing Registry (IRR).

   The IRR consists of several IRR Databases containing objects in the
   Routing Policy Specification Language (RPSL) [RFC2622] [RFC4012],
   such as route origins, sets of routes and autonomous systems, and
   routing policies.  Network operators use this data to configure route
   filters, among other things.  IRR Databases are commonly queried with
   the WHOIS protocol [RFC3912], which returns RPSL text.

   Several RIRs operate IRR Databases alongside their registration
   databases, and already provide their other registration data through
   RDAP.  Serving IRR objects through RDAP lets clients use one protocol
   for both, and relate IRR objects to the IP networks and autonomous
   system numbers they refer to.

   This document defines RDAP object classes and lookups for IRR
   objects, so that IRR data is available in the same structured JSON
   format and over the same HTTPS transport as other RDAP data.

3.  Extension

   This document defines a new RDAP extension with identifier "irr0",
   for accessing Internet Routing Registry (IRR) data through RDAP.
   This extension adheres to the guidelines in
   [I-D.ietf-regext-rdap-extensions].  New versions of this extension
   will use different extension identifiers.

4.  Lookup Path Segment specification

   Section 3.1 of [RFC9082] defines the simple lookup path segments for
   types: "ip", "autnum", "domain", "nameserver", and "entity".

   This document aims to extend this to add following path segments:

   *  "irr0_route" -- Used to identify ROUTE object and associated IP
      address prefix and the autonomous system (AS) that originates it

   *  "irr0_routeSet" -- Used to identify route-set object

   *  "irr0_autnumSet" -- Used to identify as-set object

   *  "irr0_rtrSet" -- Defines the name of the rtr-set

   *  "irr0_peeringSet" -- Specifies the name of the peering-set

   *  "irr0_filterSet" -- Defines the name of the filter

5.  The Route Object Class

   It is the RDAP representation of the RPSL route class defined in
   Section 4 of [RFC2622]

   Syntax: irr0_route/< IP prefix of the interAS route >/< AS that
   originates the route >

   For example, the following URL would be used to find information
   describing route object

   https://example.net/irr0_route/192.0.2.0/24/64500

   The route object class can contain the following members:

   *  "objectClassName" -- the string "irr0_route"

   *  "handle" -- a string representing the registry-unique identifier
      of the route object

   *  "route" -- a string representing the address-prefix for which a
      route is referenced; as per Section 4 of [RFC2622]

   *  "origin" -- a string representing an autonomous system number for
      which a route is referenced; as per Section 4 of [RFC2622]

   *  "routeVersion" -- a string signifying the ip protocol version of
      the network: "v4" signifies an route with ipv4 network, and "v6"
      signifies a route with ipv6 network

   *  "remarks" -- see Section 4.3 of [RFC9083]

   *  "pingable" -- an array of strings each containing a value as
      specified in Section 2 of [RFC5943]

   *  "holes" -- an array of strings each containing a value as
      specified in Section 8.1 of [RFC2622]

   *  "member-of" -- an array of strings, each containing a value as
      specified in Section 5.2 of [RFC2622]

   *  "inject" -- an array of strings, each containing a value as
      specified in Section 8 of [RFC2622]

   *  "components" -- a string containing a value as specified in
      Section 8.1 of [RFC2622]

   *  "aggregateBoundary" -- a string containing a value as specified in
      Section 8.1 of [RFC2622]

   *  "aggregateMtd" -- a string containing a value as specified in
      Section 8.1 of [RFC2622]

   *  "exportComps" -- a string containing a value as specified in
      Section 8.1 of [RFC2622]

   *  "entities" -- an array of entity objects as defined by Section 5.1
      of [RFC9083]

   *  "links" -- see Section 4.2 of [RFC9083]

   *  "port43" -- see Section 4.7 of [RFC9083]

   *  "events" -- see Section 4.5 of [RFC9083]

   The following is an example of the JSON object

   {
     "objectClassName": "irr0_route",
     "handle": "192.0.2.0/24AS64500",
     "routeVersion": "v4",
     "origin": "64500",
     "route": "192.0.2.0/24",
     "pingable": [ "192.0.2.1" ],
     "holes": [ "192.0.2.64/26" ],
     "member-of": [ "RS-FOO", "RS-BAR" ],
     "remarks": [
       {
         "description": [
           "She sells sea shells down by the sea shore.",
           "Originally written by Terry Sullivan."
         ]
       }
     ],
     "inject": [
       "upon HAVE-COMPONENTS {192.0.2.0/25, 192.0.2.128/25}"
     ],
     "aggr-mtd": "outbound AS-ANY",
     "aggr-bndry": "AS64500 OR AS64501",
     "export-comps": "{192.0.2.128/26}",
     "components": "{192.0.2.0/24^-}",
     "entities": [
       {
         "objectClassName": "entity",
         "handle": "XXXX",
         "roles": [ "registrant" ]
       }
     ],
     "links": [
       {
         "value": "https://example.net/irr0_route/192.0.2.0/24/64500",
         "rel": "self",
         "href": "https://example.net/irr0_route/192.0.2.0/24/64500",
         "type": "application/rdap+json"
       }
     ],
     "events": [
       {
         "eventAction": "registration",
         "eventDate": "1990-12-31T23:59:59Z"
       },
       {
         "eventAction": "last changed",
         "eventDate": "1991-12-31T23:59:59Z"
       }
     ]
   }

6.  The SET Object Class

   Section 5 of [RFC2622] defines SET objects.  This section aims to
   represent SET classes in RDAP representation.  Support for peering-
   set, rtr-set and filter-set is optional and may be provided at the
   discretion of the implementation.

   Section 5.2 of [RFC2622]

   describing route-set object

   https://example.net/irr0_routeSet/RS-FOO

   *  "objectClassName" -- the string "irr0_routeSet"

   *  "handle" -- a string representing the registry-unique identifier
      of the routeSet object.

   *  "members" -- an array of strings, each containing a value as
      specified in Section 5.2 of [RFC2622]

   *  "mp-members" -- an array of strings, each containing a value as
      specified in Section 4.2 of [RFC4012]

   *  "remarks" -- see Section 4.3 of [RFC9083]

   *  "port43" -- see Section 4.7 of [RFC9083]

7.  Autnum Route Policies

   Section 3.1.2 of [RFC9082] defines the lookup for autnum objects.
   The returned autnum object May include an "irr0_policies" member.
   "irr0_policies" is an optional member and must be an array, the order
   of the objects in the array is to be observed during processing.

   "irr0_policies" can contain following object member and each of them
   is a string containing a value as specified by RPSL:

   *  "import" -- see Section 6.1 of [RFC2622]

   *  "mp-import" -- see Section 2.5 of [RFC4012]

   *  "import-via" -- see [I-D.ietf-grow-rpsl-via]

   *  "export" -- see Section 6.2 of [RFC2622]

   *  "mp-export" -- see Section 2.5 of [RFC4012]

   *  "export-via" -- see [I-D.ietf-grow-rpsl-via]

   An example "irr0_policies" data structure:

   "irr0_policies": [
     { "import-via": "ASXXX from AS-ANY EXCEPT (ASXXX AND ASYYY) accept ANY" },
     { "export-via": "ASXXX to AS-ANY EXCEPT (ASXXX AND ASYYY) announce AS-YYYY" }
   ]

8.  RDAP Conformance

   A server that supports the functionality specified in this document
   MUST include the "irr0" string literal in the "rdapConformance" array
   (Section 4.1 of [RFC9083]) of any response containing an object class
   or member defined in this document, as well as in the help response.

10.  Privacy Considerations

   The lookups defined in this document may affect the privacy of
   entities in the registry (and elsewhere) in various ways: see
   [RFC6973] for a general treatment of privacy in protocol
   specifications, and Section 4 of [RFC7481] for specific discussion
   about privacy threats with respect to the registration data provided
   by RDAP.  Server operators should be aware of the tradeoffs that
   result from implementation of this functionality.

   Many jurisdictions have laws or regulations that restrict the use of
   "Personal Data", per the definition in Section 3.2 of [RFC6973].
   Given that, server operators should ascertain whether the regulatory
   environment in which they operate permits implementation of the
   functionality defined in this document.

11.  Security Considerations

   [RFC7481] describes security requirements and considerations for RDAP
   generally.  Additionally, guidance as to the use of TLS has changed
   since that document was published: see [BCP195] for further detail.

   Section 8 of [RFC9082] includes security considerations relating to
   object retrieval in RDAP.  Those considerations are relevant here as
   well.
